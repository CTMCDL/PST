# Running the notebooks

Install the [software environment](ENVIRONMENT.md), select the `PST (Python 3.11)` kernel, and run each notebook from its containing directory. Input and output paths are relative to that directory.

The repository includes the ion-channel XLSX data, repressilator task arrays, and the GS-ST oscillator baseline. Training workflows generate the remaining results, weights, reference trajectories, checkpoints, and figure exports. Saved notebook outputs can be viewed without execution.

## Execution modes

The default settings implement the full research protocols and can require substantial memory and runtime. Configure the workload before selecting **Run All**. Some plotting and evaluation workflows also run stochastic simulations.

| Notebook | Default setting | Execution and result reuse |
|---|---|---|
| `Dimerization/Dimerization-PST.ipynb` | `RUN_MODE = "BOTH"` | Trains both estimators. Use `RUN_MODE = "PLOT"` afterward to analyze their saved results. |
| `IonChannel/IonChannel-PST.ipynb` | `RUN_MODE = "BOTH"` | Trains both estimators using the local XLSX input. Use `RUN_MODE = "PLOT"` afterward to reuse their results. |
| `IonChannelMR/IonChannel_PST_GSST_multi_initialization.ipynb` | `cache_only = False` | Computes missing runs in `ion_channel_multiinit/` and reuses compatible completed runs. Set `cache_only = True` to require saved results. |
| `Oscillator/Oscillator-run.ipynb` | `OVERWRITE_FINAL = False` | Trains ten PST runs of 3,000 epochs. On subsequent runs, reuses completed per-run checkpoints or the final aggregate result. |
| `Oscillator/Oscillator-analysis.ipynb` | `RUN_MODE = "PLOT"` | Loads the generated PST result and included GS-ST baseline, then simulates two 300,000-event display trajectories. Run the training notebook first. |
| `RepressilatorPST/RepressilatorPST.ipynb` | `RUN_MODE = "AUTO"` | Generates missing reference data and inference results. Use `RUN_MODE = "PLOT"` to require compatible results; plotting also computes a target ODE solution and two stochastic display ensembles of 50,000 trajectories each. |
| `RepressilatorBurgerLoss/RepressilatorPST_BL.ipynb` | `RUN_MODE = "AUTO"` | Runs the log-of-ensemble-mean experiment, with the same result-reuse and display-simulation behavior as the main repressilator notebook. |
| `MNIST/MNIST-PST.ipynb` | `TRAIN_MODE = True` | Downloads MNIST on first use, trains, and saves weights, history, and test data. `TRAIN_MODE = False` loads those files and runs Monte Carlo evaluations. |
| `Timing/PST_GSST_coherent_GPU_CPU_benchmark.ipynb` | `FORCE_RERUN = False` | Measures enabled profiles when their timing JSON files are absent; otherwise reuses those files. Set `FORCE_RERUN = True` for new measurements. |
| `Timing/PST_GSST_benchmark_PST_SSA_XLA_sampler.ipynb` | Fresh measurements | Generates missing reference data and collects new timings whenever the measurement cell runs. |

Settings are near the start of each workflow. Use separate output paths when changing a protocol or preserving an earlier experiment.

## Oscillator training and analysis

Run `Oscillator-run.ipynb` before `Oscillator-analysis.ipynb`. The training notebook generates the PST result required by the analysis:

| File in `Oscillator/` | Source |
|---|---|
| `experiment_results_pst_3000_stateless_categorical.pkl` | Generated by `Oscillator-run.ipynb` |
| `oscillator_results_gsst_vilar_saiz.pkl` | Included GS-ST baseline |

Keep both filenames unchanged. The analysis loads these files without retraining either estimator. The original GS-ST training workflow is not included.

With `OVERWRITE_FINAL = False`, the training notebook validates and reuses a complete PST result when one exists. Otherwise, it uses completed per-run checkpoints and trains the remaining runs. Checkpoints are written to `pst_3000_stateless_categorical_checkpoints/`, as configured by `CHECKPOINT_DIR`.

To replace the aggregate result, set `OVERWRITE_FINAL = True` or move the existing result to a backup location. To train all ten runs again, also move the checkpoint directory to a backup location. No PST result or checkpoints are included in the repository.

## MNIST evaluation

The first training run downloads MNIST through `tf.keras.datasets.mnist`, unless the dataset is already in the local Keras cache. It then saves the model weights, history, and test data in `saved_resultsF2/`.

Set `TRAIN_MODE = False` to load these files for evaluation. Evaluation includes additional stochastic predictions and a six-by-six Monte Carlo accuracy grid, so it can remain computationally expensive after training is complete.

The final figure cell first reuses a compatible in-memory accuracy grid, then checks `saved_resultsF2/grn_mnist_FigureSx_accuracy_grid.npz`. If neither is available, it computes and saves the grid, including when `RECOMPUTE_ACCURACY_GRID = False`.

## Timing profiles

The coherent benchmark launches `pst_gsst_gpu_cpu_benchmark_worker.py` in a separate process for each device profile. Both primary profiles are enabled by default. GPU selection uses `PST_BENCH_GPU_ID`, then `CUDA_VISIBLE_DEVICES`, then device `0`. Set `RUN_GPU_PRIMARY = False` to run only the CPU profile; the optional single-thread CPU diagnostic is disabled by default.

| Profile | Ion-channel trajectories | Oscillator trajectories | Warm-ups | Repeats |
|---|---:|---:|---:|---:|
| GPU primary | 262,144 | 204,800 (8,192 starts × 25) | 3 | 18 |
| CPU primary | 32,768 | 25,600 (1,024 starts × 25) | 2 | 12 |

The ion-channel workload uses 20 event slots per trajectory; the oscillator workload uses 150. CPU trajectory counts are one eighth of the GPU counts. Compare methods within each profile: absolute GPU and CPU times reflect different workload sizes.

Missing oscillator references are generated before timing and saved for reuse. The GPU reference is `reference_trajectory.npz`; the CPU reference is `reference_trajectory_cpu_quick.npz`. The CPU filename is a cache name, not an execution-mode setting.

The coherent benchmark reuses timing JSON files by filename without checking their configuration. After changing a workload, choose a new output location or set `FORCE_RERUN = True` to collect new measurements. The standalone XLA sampler benchmark uses the full GPU workloads with three warm-ups and 20 repeats, and collects fresh timings on each execution of its measurement cell.

## Headless execution

Use `nbconvert` to execute a notebook without opening JupyterLab. This example runs Dimerization with its default `RUN_MODE = "BOTH"`, training both estimators and writing a separate executed notebook. From the repository root:

```bash
cd Dimerization
CUDA_VISIBLE_DEVICES=0 python -m jupyter nbconvert --to notebook --execute \
  Dimerization-PST.ipynb --output Dimerization-PST.executed.ipynb \
  --ExecutePreprocessor.kernel_name=pst \
  --ExecutePreprocessor.timeout=-1
```

Results and figures are written in the notebook directory. The separate output filename preserves the original notebook and its saved cell outputs.

## Running on four GPUs

Activate the environment and launch from the repository root:

```bash
conda activate pst
bash run_all_4gpus.sh
```

The launcher checks CUDA-enabled TensorFlow and executes a matrix product on each of GPUs 0–3. It registers the active Python environment as the `pst` kernel and runs every notebook from its containing directory.

Each notebook process sees only its assigned GPU, which appears internally as logical GPU 0. The timing worker receives the physical device selection through `PST_BENCH_GPU_ID`.

| GPU | Sequential workload queue |
|---|---|
| 0 | MNIST → Dimerization → IonChannel |
| 1 | Oscillator PST training → Oscillator analysis |
| 2 | Repressilator PST → IonChannel multi-initialization |
| 3 | Repressilator Burger loss |

The four queues run concurrently. After all complete successfully, the coherent timing benchmark and then the XLA sampler benchmark run sequentially on GPU 0. This separates timing measurements from training workloads and prevents concurrent writes to the benchmarks' shared reference file. Keep the machine free of other workloads while collecting timings.

On the first run, the oscillator queue generates the PST result before starting the analysis. Later launches reuse a complete result unless `OVERWRITE_FINAL = True`; see [Oscillator training and analysis](#oscillator-training-and-analysis) for checkpoint handling. The coherent timing notebook similarly reuses existing timing JSON files unless `FORCE_RERUN = True`.

Each launch creates `logs/4gpu_<UTC timestamp>_<process ID>/`, containing `gpu0.log` through `gpu3.log` and two timing logs. Set `PST_LOG_DIR` to choose another log directory. A failed notebook stops its queue; other queues finish, and the timing stage is skipped if any queue fails. The launcher returns a nonzero exit status on failure. Inspect the corresponding log before rerunning.

The launcher uses `--inplace`, replacing saved notebook outputs with the new run's outputs. Copy the notebooks first if you want to preserve both versions.

## Reruns and reproducibility

Cache compatibility depends on the configuration and method. Keep seeds, objective definitions, ensemble sizes, and sampler choices consistent when comparing estimators under the same protocol.

The main repressilator experiment uses `LOSS_MODE = "relative"` for relative mean-squared error. Its cache filenames contain the legacy token `target_scaled_log`, which is also the name of a distinct selectable loss. Use `LOSS_MODE` to identify the active objective. The separate Burger-loss experiment uses `LOSS_MODE = "log"` for the log-of-ensemble-mean objective.

Record the environment and hardware alongside new results. Stochastic trajectories and wall-clock timings can vary across devices and software versions even with the same seeds.
